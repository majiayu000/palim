# 0.3.1 history checks and ordinary / exact-number measurements

2026-10-15. Palim library/benchmark source baseline:
`2f7f1504602a09eaa902614486b46ae7c7585786`. No diff algorithm, public API,
numeric option or package version was changed for this check.

## Evidence and application fit

The existing `examples/id_list_history.rs` now checks ID move + edit, removal /
insertion, serialized delta undo/redo, reopening an initial checkpoint and replay,
and rejection of a saved change for a different application revision. It also
shows that applying a valid delta to a document with an unrelated concurrent edit
can succeed yet produce the wrong intended target. The example rejects that
stale revision **before** invoking Palim; it does not add library-level versioning.
A real application must atomically check its own trusted immutable revision while
writing. The linear example is not concurrency resolution or branching history.

A second sequence uses the field shape of Helixflow `WorkflowGraph`, `GraphNode`
and `GraphEdge`, read from local commit
`2667a00763956210db0bd29c4bdd214842ad6fba` on
`feat/canvas-agent-operate-board`. It changes a node's position and parameter,
then adds a node and edge. Nodes are an ID-keyed **map**, and edges have no stable
ID; neither was converted to an ID array to manufacture a move advantage.

All values and operations are **simulated**, not captured user history. Node type
strings are illustrative and were not validated against Helixflow's runtime
catalog. That checkout currently has no Palim dependency; its undo route reads a
verified immutable graph snapshot and creates a restore version. We did not
modify it, run it or substitute Palim for its storage. The older
[internal integration record](../internal-integration-20261007/REPORT.md) concerns a
different revision and remains historical evidence of proposal comparison, not
adoption of delta-based undo. No production/user history or independent consumer
was obtained in this task.

Both ordinary and exact-number example runs passed every assertion:

- ID-list history: 2 serialized changes, 241 bytes including base revisions.
- Workflow-shaped history: 2 serialized changes, 331 bytes including base revisions.
- Undo, redo, reopened replay and application stale-revision rejection pass.

This demonstrates a usable mechanism and its boundary. It does not demonstrate
user demand, storage savings for a real history, or an advantage over Helixflow's
existing snapshot restore. Further algorithm expansion is not justified by this
small check alone. CI now executes the history example in both numeric modes.

## Current-version measurements

Two deterministic fixtures are generated by `tools/history-fixtures.py`:

1. `id-history-2000`: rotate 2,000 identified tasks, edit the moved task, remove and
   insert another task. The native delta contains an actual move plus edits.
2. `helixflow-schema-2000`: 2,000 nodes / 1,999 edges using the actual map/edge field
   shape, edit position and temperature for 100 nodes, then add a node and edge.
   This is a scaled synthetic shape, **not** an observed production graph size.

Both modes read identical fixture bytes. Numeric values are small integers and
exactly representable binary fractions (0.5 / 0.75 / 1.5 etc.); these inputs do not
measure arbitrary-precision correctness or difficult decimal rounding. Existing
numeric contract tests cover that separate requirement.

Rust 1.95.0, release, Apple M3 Max / macOS arm64, 128 GiB RAM. The host was shared:
1-minute load average was **27.46–29.91** during measured processes, with other
builds active. These are local observations, not isolated benchmark results or
an overall performance ranking.

Each mode has three independent process runs per fixture, alternating mode order.
The existing `fixture_runner benchmark` produces five timed batches per process;
this table takes the median of the three process medians. No new benchmark engine
was added. Peak RSS is `/usr/bin/time -l` maximum resident set size in bytes and
includes process startup, retained parsed inputs and verification, not only diff
allocations. [measurements.json](measurements.json) preserves the five sorted
batch timing samples per process for diff and pipeline, but only per-process
medians for patch and reverse. The patch/reverse table values can be recomputed
from those process medians; their within-process batch samples were not retained,
so batch-level variability cannot be inspected or process medians independently
recomputed from raw samples for those stages. Load observations, binary/input
hashes and the full environment are also recorded there.

| Workload / mode | Diff ms | Parse→diff→serialize ms | Patch ms | Reverse ms | Median peak RSS bytes | Delta bytes |
|---|---:|---:|---:|---:|---:|---:|
| ID history / ordinary | 0.4438 | 1.9104 | 0.4139 | 0.0022 | 14,761,984 | 278 |
| ID history / exact | 0.4645 | 2.3191 | 0.4993 | 0.0025 | 15,532,032 | 278 |
| Workflow shape / ordinary | 1.5813 | 6.3676 | 1.6153 | 0.1500 | 42,795,008 | 9,841 |
| Workflow shape / exact | 1.6267 | 7.3682 | 1.7436 | 0.1695 | 44,089,344 | 9,841 |

Every process verified forward patch and reverse restoration before timing.
Separate `generate` runs verified RFC export/application; ordinary and exact
produced identical native delta, inverse and RFC output on these fixtures.
The observations favor ordinary mode here; they are not a reason to disable exact
numbers when the application's numeric contract requires them. Cargo unifies
serde_json features across a consumer dependency graph; the ordinary numbers
label describes this isolated Palim build, not every downstream dependency graph.

## Reproduction

```sh
python3 tools/history-fixtures.py /tmp/palim-history-workloads
CARGO_BUILD_JOBS=2 cargo +1.95.0 build --release --example fixture_runner --locked
cp target/release/examples/fixture_runner /tmp/palim-ordinary
CARGO_BUILD_JOBS=2 cargo +1.95.0 build --release --example fixture_runner --features exact-numbers --locked
cp target/release/examples/fixture_runner /tmp/palim-exact
/usr/bin/time -l /tmp/palim-ordinary benchmark /tmp/palim-history-workloads/id-history-2000.json
/usr/bin/time -l /tmp/palim-exact benchmark /tmp/palim-history-workloads/id-history-2000.json
/usr/bin/time -l /tmp/palim-ordinary benchmark /tmp/palim-history-workloads/helixflow-schema-2000.json
/usr/bin/time -l /tmp/palim-exact benchmark /tmp/palim-history-workloads/helixflow-schema-2000.json
cargo +1.95.0 run --example id_list_history --locked
cargo +1.95.0 run --example id_list_history --features exact-numbers --locked
```

Repeat each measurement three times, alternating mode order. On Linux use
`/usr/bin/time -v` and convert RSS from KiB. Fixture file SHA-256 checksums:

- ID history: `13f4256bb3a6fa1652bb76c35cf4409e4724157a6e9e2fc07919cfb6096ac2e8`.
- Workflow shape: `07ce4310ea5d2c56b323c72f3f474d3f9bccc6a3b92bbeb61817e780c9e546f6`.

The current patch changes examples, their CI invocation and evidence only. It is
not a publication, a consumer deployment or an acceptance receipt for real users.

## Local verification

Rust 1.95.0: ordinary debug/release each passed 188 tests + 2 doctests; exact-number
debug/release each passed 205 tests + 2 doctests. Both strict all-targets Clippy
configurations and fmt passed. The final history example passed in both modes.
Rust 1.85 library checks passed with ordinary and exact numbers. `git diff --check`
passed. The first example Clippy run identified an explicit loop counter; the
reopened revision now advances from the accepted saved base, and final Clippy
runs pass. The timed benchmark executable was unchanged by that example fix.

No new cross-platform CI, JavaScript interop or fuzz run was performed locally;
those existing remote gates remain relevant for library changes. No commit was
pushed and no release was published by this task.
