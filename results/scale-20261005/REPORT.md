# Palim 大规模性能实测（2026-10-05）

## 结论

本轮测到 10 万字段修改、100 万元素旋转、5000 个约 1 KB 对象成员迁移，以及 2 万元素完全替换。普通路径在这些输入上仍能完成，保护模式存在明确的数组瓶颈。结果仅针对下表的合成输入和生成 API，不是吞吐量、P99、并发服务或竞品排名。

当前候选为工作区未提交的 guard 构造优化；所有 10 个模块的源码哈希在测量前后均与上一轮冻结候选一致。基线是已发布 0.1.4，commit `50c72d59fd02d8a0e642100ad30be0771fb4eab0`。本轮没有修改 Rust 源码、Cargo 文件或已有 benchmark。

## 方法和边界

- 机器：Apple M2 Max，96 GiB 物理内存；macOS 26.5.2 arm64；Rust 1.97.0 release。计时任务逐个进程执行，不并行跑两组 benchmark。其他系统活动未隔离，百万项旋转的三个进程中位数有约 210–245 ms 的波动。
- 35 个输入/模式组合；当前候选全部测量，已发布 0.1.4 对照其中 6 个大规模保护组合。每版 3 个默认分配器计时进程，每进程 3 次热身、至少 10 ms 校准（上限 2048 次）、9 个批次。表格为三个进程中位数的中位数。另用单独计数二进制每输入/模式/版本测一次分配，共 164 条记录。
- 计时包括：已经解析的 Value / typed Patch → 公共 diff 或 inverse API → 输出销毁。不包括输入解析、最终 JSON 序列化、独立验证。inverse 的原始 typed Patch 在计时前准备。
- plain 关闭 factorize/rationalize；plain-guarded 另外开启 tests。optimized 开启 factorize/rationalize，guarded 再开启 tests。inverse 和 inverse-guarded 分别调用两个公共逆向 API，不能把它们当作 diff。所有测试使用默认 DiffOptions，仅配置提取对象 id 的 object_hash 回调，字符串数组没有 id。
- 标量负载为所有字段 Replace；旋转为最后一个元素移到开头；disjoint 为所有旧字符串替换为无共同元素的新字符串；迁移保留上一轮每成员约 1 KB 的 payload、唯一 component 和额外 Copy；撤销负载为原始 patch 连续删除数组首部 n 次，再测生成逆向插入 patch。
- 每个进程都在计时外用 json-patch 4.2.0 应用生成补丁、核对目标，再用生成逆向恢复原值。所有重复输出哈希一致，6 个对照组合与 0.1.4 的输出哈希也一致。
- 每进程 180 秒上限，35 组全部完成，没有超时或失败。完全替换只测至 2 万项；带保护的数组撤销只测至 1024 次。百万项只测旋转，不能推出百万项完全替换也能快速完成。

## 增长曲线和剩余成本

1. **普通标量和对象迁移：** 2000 → 100000 字段，plain 1.267 → 84.766 ms，规模 50 倍、耗时约 66.9 倍；guarded 2.684 → 162.679 ms，约 60.6 倍。800 → 5000 对象迁移，optimized 6.375 → 45.961 ms，guarded 11.352 → 79.383 ms。此组没有数组保护的二次增长，但不能声明严格线性。
2. **百万项旋转：** 100000 → 1000000 项，optimized 13.408 → 235.004 ms，规模 10 倍、耗时约 17.5 倍；guarded 23.998 → 332.819 ms，约 13.9 倍。普通结果仅 1 条 Move/44 B，生成仍需遍历并持有工作结构。小补丁并不等于小的计算或内存成本。
3. **完全替换数组的保护估算：** 2000/10000/20000 项 guarded 为 21.140/431.448/1652.908 ms；1 万 → 2 万约 3.83 倍，普通 optimized 为 12.571 → 26.534 ms。最终保护输出只有 2 条操作，2 万项输出 0.680 MB。源码 `rationalize` 在压缩候选前调用 `guarded_operation_bytes` 遍历原操作；数组 Add 的 `guard_add_value` 返回整个父数组，`bytes` 遍历其序列化内容。逐步增长父数组的遍历量为 0+1+…+(n−1)，这个环节本身是 O(n²)。现有成本复用只适用连续同父对象 Move，不覆盖数组 Add。这与测量增长一致，构成下一步优化的明确目标；本轮未做 CPU profile，不能给出该环节的精确耗时占比。
4. **带保护的数组逆向插入：** 128/512/1024 次 inverse-guarded 为 1.717/26.405/107.668 ms；512 → 1024 时间约 4.08 倍。1024 次普通 inverse 为 1.238 ms。每次插入都会生成完整父数组 Test，导致最终 2048 条操作、7.442 MB 输出和 56.399 MB 额外存活分配请求峰值。此处现有输出本身随规模接近二次增长，仅减少操作外壳分配无法解决。未来可以研究在保持保护范围和错误语义的前提下压缩逆向补丁；此能力尚未实现。

以上涉及源码算法的行为已核对；关于总耗时的主要来源是源码和规模曲线支持的判断，没有把它写成 profile 测出的百分比。没有把任意机器、任意输入或任意服务的表现外推为已验证。

## 证据与复现

`measurements.json` 保存环境、35 组汇总、164 条计时/分配记录和 5 条 RSS 记录；`evidence.zip` 保存两版冻结源码、probe 源码和锁文件、测量输入、原始环境、驱动脚本与 SHA-256 清单。原始 release 二进制哈希在环境中保留；源码和每个测量 fixture 的哈希均核对。

解压后执行 `python3 build-probes.py . rebuilt`，再执行 `python3 scale.py rebuilt rerun`。重建需要 Rust/Cargo 和锁文件依赖，scale 驱动的 CPU/内存读取命令为 macOS sysctl；跨平台需要按当地接口替换这两条环境读取命令，不改变测量逻辑。新构建路径/工具链可能改变二进制哈希，所以重建脚本记录自己的哈希，原始证据仍保留在本包。RSS 脚本默认原测量临时目录路径，仅用于记录原始补测方法；复测时将其两条根目录变量改为新的构建/输出目录。

本轮所有 164 条记录均完成正向/逆向核验，计数探针 final_live_delta 为 0，5 条 RSS 记录也核验相同输出。未重复运行上一轮完整测试/Clippy/fuzz，本轮没有实现代码修改。未提交或发布本报告。

便携复现检查：实际从包内两版源码重新构建了 timing/allocation 四个二进制，重放 1 万字段 plain-guarded；四个输出哈希均与原始测量一致，正向/逆向核验通过。没有重复完整 35 组计时。
